# Additional context signals: research and implementation

2026-11-03. Target: **Minecraft Java 26.3, vanilla resource packs**. The editor is an authoring tool only. This report records implemented resources and synthetic graphics evidence; clean Minecraft OpenGL/Vulkan device validation is still pending.

## What is available

The important distinction is between a value received/resolved by the client, a value bound to a particular shader, and a value available to the full-screen post chain. Environment attributes do not automatically become post uniforms. The inspected renderer sets Fog to NONE before post effects; LightmapInfo is bound only to the lightmap-generation pass. Declaring either block in grading GLSL would not recover world inputs.

| Context control | Actual input and resolution | Does it require visible sky / haze / lights? | Limits |
| --- | --- | --- | --- |
| Resolved fog colour | `Fog.FogColor.rgb`, resolved world fog at camera | No. Nearby terrain receives this even when its fog contribution is zero | Atmospheric fog mixes fog and sky attributes, weather-darkened sky, render-distance-dependent sky mix and a sunrise/sunset component depending on camera direction. Void/status darkness, world darkening and night/water vision can further alter it. Underwater, lava and powder snow replace the colour source. |
| Resolved fog start/end | `FogEnvironmentalStart/End`, blocks | No | Weather changes air ranges; boss/status effects constrain or replace them. Underwater end is multiplied by water vision with a 0.25 minimum. Render-distance boundary start/end are different values and are deliberately not exposed as biome signals. |
| Resolved sky/cloud fog end | `FogSkyEnd/FogCloudsEnd`, blocks | No: the world Fog block carries them on terrain too | Capped by render/cloud distance. Water/status/boss fog may replace the values. Clouds can be disabled while the numeric input remains available. |
| Ambient light colour | `LightmapInfo.AmbientColor` from camera attribute probe | No | Raw colour before night-vision composition, brightness/gamma, surface light levels and darkness. Biome/dimension/timeline modifiers and interpolation still apply. Does not identify a biome or measure local ambient illumination. |
| Block-light tint | `LightmapInfo.BlockLightTint` from camera attribute probe | No torch need be visible or illuminate the camera | Raw configured tint, independent of the flickering block-light multiplier. Global to the view; not per torch. Often a more stable **custom signal** than rendered fog colour, but normally shared by many environments. |
| Skylight colour | `LightmapInfo.SkyLightColor` from camera attribute probe | No | Raw lightmap colour, distinct from visible `sky_color`, sky factor and a surface's skylight level. It can still vary through environment timelines. |
| Night-vision colour input | `LightmapInfo.NightVisionColor` from camera attribute probe | No | Configured colour is present even without the effect. This control is expressly not an effect-active condition. |
| Terrain vertex tint | Terrain vertex `Color.rgb`, before multiplication by the lightmap, interpolated over the primitive | Needs matching solid/cutout terrain on-screen | Can include baked shading/AO and blended corner colours. Grass and foliage are examples, not exclusive types. Any matching tint can trigger it, including white untinted blocks for a white selector. It describes visible surfaces, potentially in another biome, not the camera's biome. |

Colour conditions support raw RGB matching or peak-normalized hue, with maximum per-channel error as tolerance (0–1). Hue ignores brightness, rejects an almost-black input below 0.001 peak, and cannot use black as a target. RGB can intentionally match black ambient colour. Numeric ranges are inclusive and hard-edged; the transport carries boolean membership, not continuously feathered weights. Existing layer strength and camera-height feather remain available.

## Underwater fog, grass, foliage and water: boundaries

`visual/water_fog_color`, `water_fog_start_distance` and `water_fog_end_distance` are real synchronized environment attributes. When submerged, vanilla puts their **resolved results** into the same Fog members used for air. The Fog block has no medium/status discriminator. The new resolved-fog controls therefore work on these results, but cannot promise “water only”, or distinguish an intentionally identical air value from water. No separate misleading underwater-only selector is offered.

Grass/foliage/water colours are baked into mesh vertex colour, rather than supplied as a global camera tint uniform. Texture RGB is a different signal. Vanilla's translucent water cannot safely carry this marker: its alpha is needed for composition. Accordingly the surface-tint control covers opaque/cutout terrain only. A water-only view supplies no surface-tint signal. Distinct grass-only, leaves-only and water-only identities are not implemented. Adding those names as aliases of a generic colour test would misrepresent coverage.

The pinned `BiomeSpecialEffects` codec still contains surface `water_color`, `foliage_color`, `dry_foliage_color`, `grass_color` and `grass_color_modifier`; these differ from synchronized environment lighting attributes. `BiomeColors` asks the world for a tint at the **block position**, using separate grass/foliage/dry-foliage/water resolvers. The mesher applies the selected tint and lighting before the vertex shader gets `Color`. Block tint sources are not one-to-one with biomes: vanilla spruce and birch leaves use fixed colours; oak, jungle, acacia, dark-oak and mangrove leaves/vines use foliage tint; other coloured surfaces include redstone, stems, sugar cane and lily pads. Grass-block sides also include untinted material. Resource-pack tint definitions, colormaps, biome blending, shading and model geometry therefore affect a surface-tint test. The inventory records surface effect fields separately; it does not falsely infer a final vertex colour from a biome JSON value alone.

The [pinned data inventory](world-signals-26.3-inventory.json) contains every known biome's explicit candidate attributes and inherited entries. There are **67** biome definitions. For example, 58 inherit atmospheric fog colour rather than declaring it, and the Overworld dimension supplies `#c0d8ff`; nine definitions set fog colour explicitly: eight other colours, plus mangrove swamp repeating that Overworld default. This is not 67 distinguishable signatures. Sky mixing and timelines further prevent a static raw-fog table from being treated as rendered-colour IDs. New controls therefore accept explicit colours/ranges and make no biome-membership shortcuts or exact-ID claims. Existing sky groups and legacy exact-ID data retain their meanings.

For a deliberately authored world signal, a distinct raw block-light tint or ambient colour is a stronger candidate than fog RGB: neither waits for visible sky/haze and their classification happens before gamma/night-vision composition. This is an inference from the inspected input paths, not a clean-client reliability measurement. Setting an environment attribute requires world/server data; **no datapack is required to use these resource-pack conditions against existing world values**, and export never silently installs one.

## Vanilla transport and scopes

1. Generate predicates for up to **four distinct active sets** of render conditions. Identical sets share a bit, including across scopes. A set combines all of its conditions with AND on the same terrain fragment. Distinct sets are evaluated independently; disabled layers keep their settings without consuming bits.
2. For lighting predicates, override the pinned `core/lightmap.fsh`. Evaluate raw LightmapInfo colours before lighting transformations and put the four-bit predicate mask into alpha, preserving the native RGB computation. Every texel receives the same metadata, so classification does not depend on a surface's sampled light level.
3. Override `include/sample_lightmap.glsl` to return native sampled RGB with alpha 1. All **seven** native 26.3 Sampler2 consumers use this helper: terrain, block, entity, item, particle, leash and text. This prevents metadata from changing opacity/discard behaviour in any of them. The terrain vertex shader separately uses an exact texel fetch to recover the mask, and passes it flat to the fragment stage. Lightmap extraction updates on its vanilla schedule (normally game ticks), not an invented per-frame attribute service.
4. In terrain fragments combine lighting bits with resolved Fog tests and vertex-tint tests. After native colour, fog, discard and chunk-visibility calculations, mark **only native alpha-1 solid/cutout** outputs. Solid has no `ALPHA_CUTOUT` define, cutout uses 0.5, sorted translucent uses 0.1; OIT accumulation and alpha-only phases are excluded. Float defines are compared in shader code, not GLSL preprocessor integer expressions. Main alpha uses complementary nibbles: `15*(1+mask)` (15 through 240). This reserves native alpha 0/255 as invalid and leaves RGB unchanged.
5. A separate 1×1 post target samples a 32×32 grid. Non-sky depth and valid complementary-nibble alpha identify candidate markers; each set needs at least three positive samples. There is no retained previous-frame state or CPU parameter upload. With an active post effect the inspected GameRenderer preserves consistent world depth and integrates hand depth before post; it does not leave the post pass with only a cleared depth target.
6. **Full-screen** scope uses those detected bits to switch grading for the whole original-scene image, including sky/entities. **Blocks only** uses each pixel's local marker bit instead. It can also be selected with no render conditions to scope a layer to marked terrain. It does not need the full-screen three-sample quorum. Recognized terrain alpha is restored to 1. Existing sky detection uses its own target and disjoint sky-depth domain. Authored terrain fog and this bridge compose in the same generated terrain overrides.

These are experimental framebuffer signals, not a separate protected data attachment. Transparent composition, overlays, partially opaque cutout pixels, framebuffer precision/format changes and other core/post packs can remove markers **or accidentally mimic a valid code**. The checksum and quorum reject many invalid values, but do not prove provenance against arbitrary alpha. Blocks only is consequently an experimental marked-terrain scope, not an exact segmentation guarantee through glass, water or overlays. It excludes unmarked blocks too, including block entities, and alpha-1 entities normally overwrite a terrain marker. Framebuffer-alpha conflict behaviour remains part of required clean-client validation. No “always available” claim is made for either new scope.

Apply and Export use `PackCompiler.files`. Core overrides load with the pack even in Command mode; `/posteffect` controls the post-grade activation, not resource loading. Pack removal restores the native resources. The existing authored-fog Command-mode restriction remains.

## Authoring and persistence

Open **Layers → Conditions → More context → Render signals / effect scope**. Select a source, enter the colour/tolerance or minimum/maximum blocks, then Add/Update. Remove edits only that source. Save signal settings returns the complete draft to Conditions; **Save conditions** commits the layer and undo history. Cancel preserves the project. The scope button selects Full-screen or Blocks only. Source help describes transformations and coverage; layer tooltips and exported README include the transport limitation.

The layer uses schema **v9** only when the new controls or Blocks-only scope are present. Older projects retain their prior versions/conditions and default full-screen meaning. Exact IDs are not converted or widened. Copy, rename, hide, grade edits and export-issue recovery preserve all render controls. Unsupported older exact-ID/time/weather/flash conditions continue to block active exports rather than being silently erased.

Layers' preview-input cycle adds **Render inputs…**. Supply each simulated raw colour/distance explicitly; missing inputs remain unavailable. There is a terrain-signal-present switch and a preview-image-as-blocks/other switch. A screenshot has no segmentation mask, so the entire specimen uses the selected scope assumption. This is a CPU reference evaluation of supplied inputs, not detection from image RGB or proof that the Minecraft bridge works.
