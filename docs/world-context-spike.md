# World context and live grading feasibility

The existing preview applies a generated static resource pack. Applying changes reloads resources, and the `end_of_frame` effect includes the HUD. It does not transfer live parameters. Both standalone export modes support only static grading; conditional layers require a separate mod renderer and must not be silently exported.

The client-side `WorldContext.capture` provides a starting point for that renderer. It snapshots the initialized camera's Y, yaw and biome, dimension ID, and the dimension's default clock in ticks modulo 24000. It returns no context without an initialized camera in the current level; biome is absent if the camera chunk is unavailable or its biome has no registry ID, and time is absent if the dimension has no default clock. Consumers should give conditions that depend on missing inputs zero weight, while unconditional layers can still apply. A dimension change or unload must reset any biome transition state. The provider stores no transition state and is not yet connected to preview or rendering.

In 26.3, `ClientClockManager.getInstance` creates an instance on demand; its public API does not expose whether a clock has received its first server update. Consequently an initial zero from an existing default clock cannot yet be distinguished from real time zero. The clock's own `partialTick` is used, but frame interpolation, custom dimension clocks and synchronization have not been verified in game. Treat these as unresolved before enabling time-based live effects.

Fabric's 26.3 level rendering events include `END_MAIN` and post-translucency hooks, but their names alone do not establish suitable scene color/depth lifetime, GUI ordering, or a writable dynamic shader uniform path. No live uniform mechanism has been proven or installed. The separate [fog rendering spike](fog-rendering-spike.md) describes the inspected frame graph, depth, projection and testing limits. Before enabling live grading, prototype per-frame parameter transfer on an actual graphics device, validate scene coverage and resource lifetimes across resize/reload and dimensions, and compare shader output with CPU layer blending. Do not reload or regenerate a pack every tick.

Verified here: compilation against the cached 26.3 APIs and pure tests for missing context, missing/invalid clocks, and tick wrapping. This does not verify world sampling, transitions, rendering or backend behavior in game.

## Per-frame uniform investigation

Cached 26.3 `PostPass` bytecode shows that JSON-defined custom uniform blocks are uploaded at construction to buffers created with `USAGE_UNIFORM` (128) only. The `customUniforms` map and `PostChain.passes` are private, and the public classes expose no uniform setter. Those buffers have neither `USAGE_MAP_WRITE` nor `USAGE_COPY_DST`, so mutating the existing post-chain block each frame through the public buffer API is not available. Replacing these buffers with managed writable ones would require an internal hook/mixin and correct GPU synchronization and cleanup; alternatively a custom render pipeline can own a writable ring buffer and issue its own pass. Neither candidate has been validated on a graphics device. In particular, successfully creating a uniform buffer or compiling a fragment does not establish that updates arrive in the intended frame on both graphics backends. The existing post-chain therefore remains static until a prototype demonstrates an end-to-end per-frame update and correct resource lifecycle.

Inspection of the 26.3 `PostPass` implementation found that its custom uniform buffers are allocated with uniform-only usage, while the buffers and pass list are private and have no public per-frame setter. Updating the existing post-chain uniforms therefore needs an internal hook that owns writable buffers, or a separate custom render pipeline and frame-graph pass. Either approach needs lifecycle, synchronization, backend and graphics-device validation before it can power the editor.

**Unverified:** it is not established that `/time set` changes the clock `WorldContext` reads. See the next actions in [v0.1-handoff.md](v0.1-handoff.md); this must be proven in game.

## Diagnostic wiring available

`/shadermaker context` now prints a camera-context snapshot in client chat, explicitly labeling the default clock as raw and synchronization as unverified. `/shadermaker capabilities` reports the current feature boundaries. The sample Context screen can copy the same snapshot into its draft with **Use world**, refusing incomplete context. Neither path promotes the clock to a synchronized input or enables live conditions. These commands need in-game validation; they cannot be invoked through the harness's server-console `command` route.
